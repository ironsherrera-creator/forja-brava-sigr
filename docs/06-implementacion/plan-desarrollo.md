# Plan de Desarrollo Priorizado (13 Etapas)
## FORJA BRAVA — SIGR

Hoja de ruta ordenada por dependencias reales para ejecutar la construcción evolutiva del sistema una vez recibida autorización independiente.

---

| Etapa | Nombre | Dependencias | Entregables clave | Criterio de salida (Verificable) |
|---|---|---|---|---|
| **01** | **Preparación y saneamiento del repositorio** | Ninguna | Desindexar `node_modules/` de Git (`git rm -r --cached`), activar `.gitignore`, commit base limpio, eliminar 4 PNG huérfanos (`menu-*.png`) y carpetas vacías, optimizar 14 imágenes activas a WebP (< 1.5 MB total). | `git status` limpio sin `node_modules`; peso total de imágenes reducido > 95%. |
| **02** | **Arquitectura objetivo y entorno frontend** | Etapa 01 | Configurar Vite + React + `@tailwindcss/vite` + React Router + Zod + ESLint; crear estructura `src/`, portar `theme.css`, `public.css`, `panels.css` y `print.css`; eliminar servidor `node -e` inseguro. | `npm run dev`, `npm run build` y `npm run lint` ejecutan con código `0`. |
| **03** | **Base de datos PostgreSQL y Storage (Supabase)** | Etapa 02 | Crear migraciones SQL para las 18 tablas, índices, restricciones de exclusión de reservas, snapshots en `order_items`, bucket `product-images` y `seed.sql` (4 categorías, 13 productos, configuración base). | Migraciones aplicadas sin errores; semilla verificada en PostgreSQL. |
| **04** | **Autenticación, roles, RLS y RPCs críticas** | Etapa 03 | Configurar Supabase Auth, trigger `handle_new_user`, trigger anti-escalamiento en `profiles`, políticas RLS en el 100% de tablas, RPCs (`create_order`, `create_table_order`, `update_order_status`, `get_available_reservation_slots`, `create_reservation`, `request_table_account_close`, `settle_table_account`, `close_cash_session`) y Edge Function `create-staff-user`. | Pruebas SQL verifican que `cliente` no puede escalar rol ni leer caja, y `mesero` no puede cambiar preparación ni cancelar pedidos fuera de `Pendiente`. |
| **05** | **Migración progresiva de base existente y componentes UI** | Etapa 02, 04 | Implementar `AuthContext`, `CartContext` (con hidratación corregida), `ToastContext`, `ProtectedRoute`, los 4 layouts y los componentes compartidos (`BrandLogo`, `Button`, `ModalDialog`, `Drawer`, `ProductCard`, `DataTable`, `PrintableReceipt`). | Navegación base y protección de rutas operativas sin errores en consola. |
| **06** | **Sitio público y menú digital** | Etapa 05 | Portar Landing editorial (`PUB-01`), Menú dinámico con buscador y filtros desde BD (`PUB-02`), construir Modal de Detalle de producto (`PUB-03`), mejorar Carrito (`PUB-04`) y conectar Contacto (`PUB-06`). | Menú carga desde PostgreSQL; cero contadores estáticos; carrito persiste al recargar. |
| **07** | **Experiencia del cliente** | Etapa 06 | Implementar Login/Registro/Recuperación (`CLI-01`, `CLI-02`), Dashboard (`CLI-03`), Perfil y Direcciones (`CLI-04`), Checkout 5 pasos con 3 modalidades/D-03/D-04/D-06 (`CLI-05`), Mis pedidos (`CLI-06`) y Seguimiento Realtime (`CLI-07`). | Cliente compra en las 3 modalidades, ve comprobante imprimible y sigue cambios de estado en vivo. |
| **08** | **Gestión de mesas y reservas automáticas** | Etapa 04, 07 | Implementar CRUD de Mesas (`ADM-07`, D-01), Reservas públicas con disponibilidad y confirmación automática (`PUB-05`, D-02, D-06), Mis reservas (`CLI-08`) y Gestión + Calendario admin (`ADM-06`). | Reservas concurrentes en misma mesa/horario son bloqueadas por BD; cancelación libera la mesa al instante. |
| **09** | **Panel operativo del mesero** | Etapa 06, 08 | Construir Dashboard mesero (`MES-01`), Mapa de mesas (`MES-02`), Toma de comanda reutilizando catálogo/carrito (`MES-03`), Pedidos registrados con límites D-05 (`MES-04`) y Cuenta acumulada + solicitud de cierre (`MES-05`, D-04). | Mesero registra múltiples comandas en una mesa, marca entrega, cancela solo en `Pendiente` y solicita cierre de cuenta. |
| **10** | **Panel administrativo completo** | Etapa 06, 08, 09 | Completar Dashboard KPI en `America/Bogota` (`ADM-02`), Productos con Storage (`ADM-03`), Categorías (`ADM-04`), Pedidos sin pérdida de filtros (`ADM-05`), Usuarios/Roles (`ADM-08`), Configuración (`ADM-12`) y Auditoría (`ADM-11`). | Todos los módulos CRUD operativos con trazabilidad en `audit_logs`. |
| **11** | **Caja y Reportes** | Etapa 09, 10 | Implementar Caja completa (`ADM-09`: apertura, base, cobro de cuentas de mesa D-04, ingresos/egresos, arqueo y cierre sin duplicar ventas) y Reportes diarios/periodo por `product_id` imprimibles (`ADM-10`). | Arqueo cuadra efectivo vs. digital sin duplicación; pedidos cancelados excluidos de ventas. |
| **12** | **Pruebas automatizadas (Vitest + Playwright)** | Etapa 11 | Suite unitaria/integración con Vitest (esquemas Zod, carrito, reglas de caja/reportes, guards) y suite E2E con Playwright cubriendo los 4 perfiles y reglas D-01 a D-06. | 100% de pruebas unitarias y E2E críticas pasando en verde. |
| **13** | **CI/CD y despliegue (GitHub Actions + Vercel)** | Etapa 12 | Configurar `.github/workflows/ci.yml` (`npm ci`, `lint`, `npm audit`, `test:unit`, `build`, `test:e2e`, chequeo secretos), `vercel.json` (rewrites SPA + cabeceras de seguridad) y variables de entorno en Preview/Production. | Pipeline verde en PR y despliegue exitoso en Vercel con cabeceras de seguridad verificadas. |
